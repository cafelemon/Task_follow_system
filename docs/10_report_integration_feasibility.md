# 4.3.0 飞书汇报集成可行性与工作台化任务治理路线

## 1. 文档用途

本文档用于给总经办、人事和系统建设侧统一口径：飞书汇报、周报材料和任务跟踪系统可以怎样连接，哪些能力可以先做，哪些能力不能在未验证前承诺。

4.3.0 只做计划安排，不新增业务功能、不新增数据库表、不制作生产离线包。本版在 4.2.1 的基础上，吸收 `4.2.1task.md` 对“待归类事项、周报中心、角色化工作台”的补充设计，明确 4.3.x 先完成执行者侧闭环，再由 4.4.x 进入任务负责人和责任人处理侧。

## 2. 结论摘要

- 系统内生成个人周报可行，可以把子任务周更新、附件、遗留事项、风险项和待归类事项汇总成个人工作材料。
- 不建议新增长期游离在任务树外的“日常任务池”。临时或急性工作应先进入“待归类事项”渠道，再由责任人判断归类、挂树、保留为补充记录或关闭。
- 工作台建议重新成为系统首页，但定位为按身份组合的个人行动台；会议看板保留为总经办会议和管理审阅入口。
- 待归类事项是补充入口，周报中心是聚合出口；正式任务统计仍以任务树和周更新为准。
- 4.3.x 聚焦执行者侧闭环：执行者进工作台、看到本人任务、提交待归类事项、查看事项状态、形成个人周报材料和历史快照。
- 责任人归类、任务负责人处理、部门负责人补部门任务、总经办秘书处理母任务缺失，统一留到 4.4.x 及后续版本。
- 直接把系统生成内容提交回飞书原生“汇报”周报，目前不能按确定能力承诺。
- 飞书官方汇报开放能力当前主要是查询规则和查询任务，未发现创建、提交或更新汇报内容的开放接口。
- 飞书绩效存在补充信息和指标数据导入能力，但它属于绩效数据归档，不等同于飞书汇报周报提交。

## 3. 背景问题

人事提出的核心诉求不是简单多一个填报入口，而是担心现有任务树没有覆盖全部工作表达，尤其是临时性、日常性、协助性事项。这个问题真实存在，但不宜直接解成“人人再填一个日常任务池”。

任务跟踪系统的主线仍应保持清晰：公司任务原则上需要能追溯到战略目标、母任务、部门任务和子任务。若某项工作长期找不到归属，通常意味着任务拆解不完整、任务口径不清楚，或它本身不是应进入公司任务管理的项目型事项。

## 4. 产品治理方案

推荐采用“待归类事项”而不是“日常任务池”。

### 4.1 主线与辅助线

系统正式任务主线保持不变：

```text
战略目标 -> 母任务 -> 部门任务 -> 子任务 -> 周更新 -> 历史记录 -> 会议看板
```

4.2.1 之后新增辅助线，但辅助线不直接改变正式任务统计：

```text
待归类事项 -> 部门任务补充 / 部门常态化工作 / 跨部门协作 / 周报补充 -> 周报中心 -> 周报材料生成
```

### 4.2 待归类事项入口

所有人的工作台都固定提供“提交待归类事项”入口。结合 `4.2.1task.md` 的补充，本轮方案把提交入口设计为低门槛但带初步归类：

- 事项内容：说明临时任务、急性任务或未被任务树覆盖的工作。
- 归类方式：提交人根据自己的理解先选一种归类方向。

归类方式首版建议为四类：

| 归类方式 | 提交时额外信息 | 4.3.x 处理边界 |
| --- | --- | --- |
| 挂载已有部门任务 | 选择关联部门任务 | 作为部门任务补充记录进入待确认和周报草稿，不自动生成正式子任务 |
| 本部门常态化工作 | 默认使用提交人所属部门 | 进入个人周报草稿，不进入正式任务树和进度统计 |
| 跨部门协作任务 | 选择协作部门 | 进入个人周报草稿；双审核能力留到 4.4.x 或更后版本 |
| 周报补充记录 | 无 | 只作为个人周报补充材料，不进入正式任务树 |

提交人不需要判断战略目标或母任务。若选择“挂载已有部门任务”，系统可以辅助识别部门任务负责人、所属部门、所属母任务和战略目标，但 4.3.x 不提供确认处理动作。

### 4.3 归类闭环

1. 员工提交待归类事项并选择归类方式，系统按归类方式辅助识别后续可能的责任链。
2. 责任人或归类处理人判断事项归属：挂到现有子任务/部门任务、需要新增部门任务、需要新增母任务，或关闭为非任务型记录。
3. 若缺部门任务，由任务负责人或部门负责人补建部门任务并继续拆解。
4. 若缺母任务，形成“母任务缺失诉求”，进入总经办秘书工作台和总经办会议流程。
5. 总经办会议确认后，由总经办/秘书按现有权限新增母任务，再由部门负责人继续拆分部门任务。
6. 关闭为非任务型记录的事项只进入个人周报材料，不进入正式任务推进统计。

4.3.x 只实现执行者提交、个人列表、责任人只读可见和周报聚合。上面的同意、退回、双审核、转子任务、部门统计和会议处理动作均是 4.4.x 及后续版本范围。

### 4.4 分类口径

| 类型 | 判断标准 | 处理方式 |
| --- | --- | --- |
| 应补拆任务 | 持续推进、可明确责任人和完成标准 | 补拆到任务树 |
| 应挂现有任务 | 与已有子任务或部门任务高度相关 | 关联到现有任务 |
| 缺部门任务诉求 | 有明确部门承接，但现有部门任务无法承接 | 由任务负责人或部门负责人补建部门任务 |
| 缺母任务诉求 | 涉及公司级方向或跨部门事项，现有母任务无法承接 | 进入总经办会议，由总经办/秘书确认是否新增母任务 |
| 非任务型记录 | 临时沟通、例行支持、无项目交付 | 保留为记录，不进入任务看板 |
| 人事考核补充材料 | 更适合作为绩效佐证 | 输出到个人材料或绩效补充场景 |

### 4.5 数据对象口径

`4.2.1task.md` 中的 `WorkItem`、`WorkItemEvent`、`WeeklyReport` 设计只作为产品方向参考，不作为最终字段清单。后续真正开发时，字段应以实现需要、权限边界、迁移风险和审计要求为准。

4.3.x 只需要覆盖执行者侧最小闭环：提交人、事项内容、归类方式、关联部门任务或协作部门、状态、提交时间、撤回时间、周次和周报快照引用。确认人、确认时间、退回原因、双审核状态、部门统计字段可以预留设计，但不开放责任人处理能力。

## 5. 工作台定位

工作台建议重新成为登录默认页，但不是回到早期“泛泛展示”的工作台，而是按身份组合的个人行动台。会议看板不取消，继续作为总经办会议、秘书主持会议和管理层审阅的专项页面。

用户拥有多重身份时，工作台模块应叠加展示，而不是只选择一个最高身份。

| 身份 | 工作台优先内容 |
| --- | --- |
| 管理员 | 通知发送失败、缺 open_id/邮箱待补人员、待启用人员、系统配置风险、本人的任务负责人/执行人事项 |
| 总经办秘书 | 部门推进异常、母任务缺失诉求、部门任务缺失诉求、高风险项、逾期项、未更新情况和会议流程入口 |
| 总经理/总经办 | 公司级关键风险、逾期、缺母任务诉求、跨部门推进异常和会议看板入口 |
| 部门负责人 | 本部门牵头母任务、待拆部门任务、部门任务缺失诉求、本部门风险和待归类事项 |
| 任务负责人 | 本人负责的部门任务、待拆子任务、执行人未更新、本人待归类事项处理 |
| 子任务执行者 | 本人待更新子任务、草稿未提交、临近截止任务、本人提交的待归类事项状态 |
| 观察者 | 只读审阅入口、全局任务追溯；如本人兼任负责人或执行人，则叠加对应行动项 |

## 6. 技术可行性

| 能力 | 可行性 | 说明 |
| --- | --- | --- |
| 读取飞书汇报规则 | 可行 | 官方接口为 `GET /open-apis/report/v1/rules/query`，权限为 `report:rule:readonly` |
| 读取飞书汇报任务 | 可行 | 官方接口为 `POST /open-apis/report/v1/tasks/query`，权限为 `report:task:readonly` |
| 读取已提交汇报内容 | 可验证 | 查询任务响应包含 `form_contents`，需要用真实规则和权限验证字段完整性 |
| 系统内生成个人周报 | 可行 | 已有子任务周更新、附件、风险和任务层级数据 |
| 飞书卡片提醒回系统填写 | 可行 | 现有飞书卡片、签名链接和点击追踪能力可复用 |
| 生成周报草稿供复制 | 可行 | 作为低风险过渡方案，不依赖飞书写入接口 |
| 自动提交回飞书汇报 | 高风险，暂不承诺 | 当前未发现正式创建/提交/更新汇报内容 API |
| 导入飞书绩效补充信息 | 部分可行 | 属于绩效数据，不等于汇报周报提交 |
| 工作台聚合身份行动项 | 可行 | 后续实现时聚合现有通知、人员、任务、风险和待归类事项，不替代原页面 |

## 7. 三方沟通口径

### 7.1 对人事

可以承认现有任务树不一定覆盖全部工作表达，但不建议让员工重复维护一个长期“日常任务池”。系统可以在工作台提供低门槛入口，让员工只填写事项和责任人，后续由责任链负责归类、补拆或关闭。

如果人事需要的是“周报材料覆盖”，系统内生成可做；如果人事要求“必须自动回到飞书原生汇报”，需要先做单独 API 和权限验证。

### 7.2 对大领导

任务管理主线不变：公司任务必须能追溯到战略目标。周报不是新的任务体系，而是任务执行结果和补充记录的汇总视图。人事考核材料可以从系统汇总，但不能反向污染任务结构。

临时事项可以先被记录，但不能长期游离在任务树外。缺部门任务、缺母任务的诉求会被暴露出来，从而反向推动任务拆解完整。

### 7.3 对总经办秘书

工作台应成为会议准备入口：集中呈现母任务缺失诉求、部门任务缺失诉求、风险、逾期和未更新情况。秘书主持会议时可以按“异常总览 -> 缺失诉求 -> 风险逾期 -> 责任确认 -> 会后跟进”的流程推进。

### 7.4 对技术

系统内汇总、展示、复制草稿和飞书提醒都没有结构性障碍。飞书汇报原生回写目前没有确定开放接口，不能作为已确认需求排期。飞书绩效 API 可以单独评估，但不能替代汇报提交。

## 8. 后续版本建议

- 4.3.0：完成执行者工作台与待归类事项分版本规划，只更新文档和版本口径。
- 4.3.1：执行者工作台框架。已新增工作台页面并作为登录默认页，展示本人待更新子任务、草稿未提交、临近截止、已完成任务和风险登记入口；暂不做待归类事项数据模型。
- 4.3.2：待归类事项提交入口。新增待归类事项底座，执行者填写事项内容并选择归类方式；挂载已有部门任务时选择部门任务，跨部门协作时选择协作部门，提交后进入待确认状态。
- 4.3.3：个人列表与状态可见。新增“我的提交”列表，展示事项内容、归类方式、关联部门任务、状态和提交时间；新增“待我确认”只读列表，让责任人能看到收到的事项但不提供处理按钮；提交人可撤回未确认事项。
- 4.3.4：周报中心草稿聚合。新增“我的周报/周报草稿”基础视图，聚合本周正式子任务周更新、待归类事项、风险与卡点、下周计划，正式任务和待归类事项分区展示，不回写飞书汇报。
- 4.3.5：周报确认、复制和历史快照。员工可生成并确认本周周报快照，确认后不受后续任务或事项变化影响，支持复制飞书汇报可用文本；导出文档如成本较高可延后到 4.5。
- 4.3.6：执行者体验收尾与 4.4 准备。优化手机端工作台、待归类事项、周报中心体验，补齐空状态、无任务状态、提交成功状态和只读责任人提示，梳理 4.4.x 所需处理字段。
- 4.4.x：进入任务负责人/责任人侧，处理归类、挂任务、关闭或上提诉求。
- 飞书汇报回写专项：只有在验证到正式提交 API 或稳定数据写入路径后再立项。
- 绩效补充信息专项：如人事确认需要绩效佐证材料，再评估飞书绩效补充信息导入。

## 9. 验证清单

- 使用飞书汇报 API 查询现有周报规则，确认规则字段、汇报对象和权限范围。
- 使用飞书汇报 API 查询已提交周报任务，确认 `form_contents` 是否能稳定返回完整文本、附件和图片信息。
- 明确记录“未找到创建/提交/更新飞书汇报内容 API”的证据。
- 收集 3 到 5 个真实临时事项例子，分别归类为挂现有任务、需要新增部门任务、需要新增母任务、非任务型记录或绩效补充材料。
- 由大领导确认“临时事项必须归类或关闭”的治理原则。
- 由总经办秘书确认母任务缺失诉求、部门任务缺失诉求、风险项和逾期项能形成会议流程。
- 由管理员确认工作台优先暴露通知失败、人员信息缺失和系统维护事项。
- 由人事确认本阶段缺口是“周报材料覆盖”还是“飞书汇报原生提交”。
- 4.3.x 每个小版本都应先由执行者真实验收，再进入下一个小版本；责任人同意/退回、双审核、部门统计和会议处理能力不得提前混入 4.3.x。
- 生产通知继续按当前暂停记录处理，本线不得顺手恢复通知。
