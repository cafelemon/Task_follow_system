# 公司工作任务跟踪系统决策记录

## 1. 文档用途

本文档用于记录项目中的关键决策、背景和影响。后续如果修改已有决策，应新增记录说明原因，不直接删除历史决策。

## 2. 决策列表

### D-001 文档文件名统一小写编号

日期：2026-06-04。

决策：`docs/` 目录采用小写编号文件名，范围为 `00_overview.md` 到 `07_decisions.md`。

背景：项目处于新建阶段，需要先建立稳定文档骨架，方便用户和 AI Coding Agent 共同维护。

影响：不再保留旧的未编号大写命名文档。界面设计内容合并到产品需求和架构文档中。

### D-002 Base 仅作为过渡和迁移来源

日期：2026-06-04。

决策：Base 可以继续承担过渡、导出、展示和历史迁移来源，但不作为新系统主业务系统。

背景：现有任务跟踪依赖飞书多维表格，但长期使用中存在历史追踪、权限、校验和展示效率问题。

影响：新系统需要建立自己的数据模型、权限模型、历史记录和流程校验。后续不能把 Base 自动化当作主链路。

### D-003 每周进展作为历史记录保存

日期：2026-06-04。

决策：每周进展必须作为独立周更新记录保存，不依赖清空字段和人工快照维持历史。

背景：原有模式中每周清空字段会破坏自然历史，用户无法直接按任务查看连续进展。

影响：数据库需要设计周更新和任务事件对象；任务详情页必须支持时间线；过去记录默认可读、可审计，不作为日常覆盖字段。

### D-004 飞书是提醒和快捷入口，复杂操作走 Web

日期：2026-06-04。

决策：飞书机器人主要承担提醒、卡片入口和轻量操作。复杂任务拆分、看板查看、历史时间线和系统管理通过 Web 页面完成。

背景：飞书卡片适合触达用户，但不适合承载复杂编辑和长期管理界面。

影响：产品和架构应优先保证 Web 主操作体验，同时设计按身份推送的飞书入口卡片。

### D-005 附件存储优先放公司 NAS

日期：2026-06-04。

决策：周更新附件和历史导入附件优先存储到公司 NAS，数据库保存附件元数据和关联关系。

背景：任务跟踪系统涉及长期填报和附件积累，不宜把大文件直接放入数据库。

影响：后续架构需要设计 NAS 挂载、路径规则、权限校验、下载接口和备份策略。

### D-006 第一版先做核心闭环

日期：2026-06-04。

决策：V1 MVP 先完成任务创建、任务拆分、每周更新、任务时间线、管理看板、飞书提醒和权限控制。

背景：日报、周报、飞书任务中心、复杂绩效等集成依赖核心任务模型稳定，不应在第一版过早引入。

影响：非 MVP 能力仅预留接口和数据关联，不阻塞核心闭环开发。

### D-007 1.0.0 技术栈定版

日期：2026-06-05。

决策：1.0.0 采用 React + TypeScript + Vite + Ant Design 作为前端栈，预留后续引入 ProComponents；采用 FastAPI + SQLAlchemy 2.x + Pydantic + Alembic + PostgreSQL 作为后端栈；本地部署采用 Docker Compose + Nginx。

背景：样板是典型企业后台系统，任务管理需要大量表格、筛选、表单、标签、看板、权限矩阵和统计卡片；后端需要多表关联、历史事件、权限查询和按周统计。

影响：仓库建立 `frontend/`、`backend/`、`deploy/` 工程结构，版本统一记录为 `1.0.0`。

### D-008 1.0.0 飞书只做预留和模拟

日期：2026-06-05。

决策：1.0.0 不接真实飞书机器人发送、组织同步和卡片回调，只保留用户 `open_id`、模拟通知记录和 Web 跳转链接。

背景：真实飞书接入依赖企业应用权限、回调地址和生产访问入口。核心任务闭环应先在 Web 系统内跑通。

影响：通知记录页面展示模拟发送结果，真实飞书能力进入后续版本。

### D-009 1.0.0 权限采用矩阵可配

日期：2026-06-05。

决策：1.0.0 权限采用“角色动作矩阵可配置 + 任务关系权限”的组合。管理员可在角色权限页调整角色拥有的动作权限，人员页单独维护预设人员、部门、角色和 open_id 绑定状态，接口层继续校验任务关系。

背景：只做固定角色后续容易难以适应总经办、部门负责人、观察角色、信息中心等边界变化。

影响：后端建立 `permissions`、`role_permissions`，前端提供人员管理和权限矩阵编辑能力。

### D-010 1.0.0 本地部署和本地附件优先

日期：2026-06-05。

决策：1.0.0 使用 Docker Compose 本地优先部署，附件默认保存到本地挂载目录，配置项预留 NAS 路径。

背景：NAS、生产反代和 HTTPS 需要现场环境确认，不应阻塞第一版可运行系统。

影响：`deploy/docker-compose.yml` 默认启动 `frontend`、`backend`、`postgres`、`nginx`，附件目录为 `data/attachments`。

### D-011 1.0.0 登录体系先以系统管理员为入口

日期：2026-06-05。

决策：1.0.0 不再使用固定 mock 用户请求头，改为系统管理员账号密码登录和 HttpOnly cookie session。普通用户的后续入口预留为 open_id + 姓名绑定。

背景：系统管理、人员预设和角色权限需要真实登录边界，不能继续依赖固定用户 ID。飞书免登仍依赖后续企业应用权限和回调入口。

影响：登录页不展示内置账号提示；后端增加 session 表、open_id 绑定接口和人员管理接口；前端按管理员权限显示人员、角色权限和 Base 同步模块。

### D-012 Base 同步不猜字段，CLI 可用前保持阻塞反馈

日期：2026-06-05。

决策：2026任务跟踪表导入必须来自真实 `lark-cli drive +search`、`base +table-list`、`base +field-list` 和 `base +record-list` 返回，不按样例字段或记忆字段手工造任务。

背景：本轮验证中，宿主机执行 `lark-cli --version` 超过 6 秒未返回；Docker backend 容器内返回 `lark-cli not found`。继续猜字段会污染正式任务数据。

影响：系统已提供管理员可见 Base 同步预览和导入入口，接口带超时和明确阻塞信息；真实任务导入需先修复 lark-cli 环境或把 CLI 能力安装进 backend 运行环境。

### D-013 1.2.0 页面按真实任务层级钻取

日期：2026-06-05。

决策：1.2.0 战略目标、母任务和部门任务页面必须按 `战略目标 -> 母任务 -> 部门级任务 -> 子任务` 的真实层级展示。母任务详情展示部门级任务，部门任务页直接展示当前部门可见的部门级任务树状总览。

背景：Excel 和 Base 中的任务编号层级已经明确，`T-001` 是母任务，`T-001-01` 是部门级任务；旧页面把母任务卡片和子任务详情混在一起，容易误导使用者。

影响：前端增加战略目标详情和母任务详情路由，后端增加按目标和母任务过滤的接口；部门任务页不再使用母任务卡片作为主入口。

### D-014 1.2.0 母任务管理按角色和负责人开放

日期：2026-06-05。

决策：母任务管理页仅对系统管理员、总经理、总经办秘书、观察者和母任务负责人开放。系统管理员、总经理、总经办秘书、观察者可查看全部母任务；母任务负责人只查看自己负责的母任务。

背景：母任务管理属于公司级任务视角，不应默认开放给所有部门成员；但母任务负责人需要能进入自己负责的母任务并查看部门级任务拆解。

影响：后端接口必须执行同样的权限过滤，前端导航只根据后端返回的能力字段显示入口。

### D-015 1.3.0 不再展示任务进度条

日期：2026-06-05。

决策：1.3.0 页面不再展示任务进度条，不再要求周更新填写进度百分比。历史 `progress` 字段暂时保留，仅用于兼容旧数据和后续可能的数据清洗。

背景：公司任务进度很难用百分比准确量化，继续展示进度条会给管理判断造成误导。

影响：工作台、战略目标、母任务、部门任务、子任务和周更新页面移除进度条；周更新保存逻辑不再依赖进度字段。

### D-016 1.3.0 周更新并入子任务执行

日期：2026-06-05。

决策：每周更新不再作为独立主菜单，统一从子任务执行页进入。草稿自动保存不写历史事件，提交后才形成正式周更新历史。

背景：执行人实际工作入口是具体子任务，从子任务进入更新更符合日常填报路径。

影响：旧 `/weekly-updates` 路由跳转到子任务执行；新增子任务周更新页，支持草稿恢复、提交和离开提醒。

### D-017 1.3.0 母任务删除采用归档隐藏

日期：2026-06-05。

决策：母任务“删除”按归档隐藏处理，不物理删除母任务、部门任务、子任务、周更新和历史事件。

背景：母任务下通常已经存在真实拆解和周更新，硬删除会破坏审计和会议材料依据。

影响：默认列表、目录和详情入口隐藏归档母任务；后续如需恢复或查看归档，可另做归档管理入口。

### D-018 1.4.0 部门级任务删除采用归档隐藏

日期：2026-06-05。

决策：部门级任务“删除”按归档隐藏处理，不物理删除部门任务、子任务、周更新和历史事件。

背景：部门级任务已经承接真实拆解和执行记录，硬删除会破坏任务追踪和会议复盘依据。

影响：母任务详情、部门任务总览和子任务执行默认隐藏归档部门任务；后续如需恢复或查询归档，可另做归档管理入口。

### D-019 1.4.0 子任务状态不再依赖进度百分比

日期：2026-06-05。

决策：子任务执行状态采用“待开启、进行中、已完成”，本周填报状态采用“待更新、已更新”，不再用进度百分比判断任务推进。

背景：1.3.0 已决定不展示进度条，1.4.0 进一步把执行状态和周更新状态拆开，避免把任务是否启动、是否本周更新和是否完成混在同一个字段里。

影响：新分配子任务需要先开启再填写周更新；本周是否已更新由当前周草稿或提交记录判断；已完成任务锁定更新表单。

### D-020 1.5.0 会议看板作为第一入口

日期：2026-06-05。

决策：系统取消工作台和风险与逾期独立入口，会议看板作为登录后和根路径默认入口。

背景：工作台和风险逾期页的信息需要服务会议汇总，而不是分散成多个低价值入口。

影响：会议看板需要承接指标卡、图表、风险逾期汇总、母任务汇总和部门汇总；旧路由保留跳转兼容。

4.2.1 修订：会议看板不再作为所有用户唯一首页的长期目标。后续工作台应恢复为登录默认页，但定位为按身份组合的个人行动台；会议看板保留为总经办会议、秘书主持会议和管理层审阅的专项入口。

### D-021 1.5.0 历史时间线采用只读周矩阵

日期：2026-06-05。

决策：历史时间线不再使用事件流样式，改为按母任务、部门级任务、子任务展开的只读周矩阵。

背景：用户需要按任务和周查看完成内容、遗留事项和附件，而不是按事件时间倒序阅读。

影响：子任务新增启动时间字段，历史矩阵按用户可读权限过滤；附件行本版先占位，后续接入真实附件。

### D-022 2.0.0 飞书先接真实出站提醒

日期：2026-06-07。

决策：2.0.0 作为 2.x 飞书阶段第一版，先接入企业自建应用真实出站消息：后端通过 app_id/app_secret 获取 tenant_access_token，按用户 open_id 发送周更新提醒卡片。暂不接飞书长连接、卡片回调和免登。

背景：现有飞书桥接系统已经证明 token 缓存、企业应用配置和消息发送链路可复用为经验；但任务系统权限更复杂，不能直接复用桥接系统的会话路由、部门判断和 FastGPT 业务逻辑。先打通真实触达，可以最小闭环验证企业应用权限、用户 open_id 绑定和 Web 跳转入口。

影响：通知记录支持 `sent`、`failed`、`blocked`、`mock_sent` 等状态；通知页新增飞书诊断和发送入口；后续 2.x 再推进免登、卡片回调、按身份卡片和飞书任务生态联动。

### D-023 2.0.1/2.0.2 先手动绑定 open_id

日期：2026-06-08。

决策：2.0.1 和 2.0.2 先采用管理员手动录入 open_id 的方式进行飞书真实触达测试。2.0.1 先跑通本人测试，2.0.2 扩展少量测试人员；飞书免登和首次使用自动绑定放到 2.0.3。

背景：当前首要目标是验证企业自建应用权限、tenant_access_token 获取、机器人消息发送、局域网 Web 跳转和通知记录状态。免登绑定会引入授权回调、身份匹配和冲突处理，过早引入会拖慢第一轮真实发送验证。

影响：人员新增和编辑需要支持 open_id 手动录入；open_id 必须全局唯一；测试卡片和周更新提醒均基于系统内人员 open_id 发送。后续 2.0.3 免登绑定仍不得覆盖系统内部门、角色和任务权限配置。

### D-024 2.0.2 飞书卡片使用签名免密码入口

日期：2026-06-08。

决策：2.0.2 飞书卡片按钮不再直接跳普通 Web URL，而是跳转服务端签名入口 `/api/auth/lark-link`。服务端验证 token 后为对应用户创建 HttpOnly session，再跳转到目标业务页面。

背景：普通 URL 只适合已有登录态的浏览器。多人测试时，测试人员通常没有系统账号密码和旧 session，如果仍要求登录，会阻塞飞书入口验证。但直接把 open_id 和姓名放进 URL 并信任也不安全。

影响：签名 token 必须包含用户、open_id、目标路径、过期时间和随机 nonce；签名无效、过期、用户停用或 open_id 变更时不能创建 session。2.0.2 仍不是完整飞书 OAuth 免登，正式免登继续放到 2.0.3。

### D-025 2.0.3 采用手机号预绑定加飞书免登混合方案

日期：2026-06-08。

决策：2.0.3 不单独依赖飞书免登来获得首个 open_id，而是先由管理员在人员档案维护手机号，通过飞书通讯录接口批量解析并预绑定 open_id；用户主动进入系统时再走飞书网页免登校验身份并创建系统 session。

背景：没有 open_id 就无法给用户推送卡片，而用户收不到卡片也无法通过卡片进入系统完成绑定。手机号换 open_id 能解决首触达问题，OAuth 免登则用于主动入口和身份校验。

影响：手机号只作为管理员预绑定和辅助匹配字段，不作为单独登录凭证；open_id、手机号或姓名冲突时必须阻塞待人工处理，不自动覆盖已有绑定。局域网测试先使用本地回调地址，生产部署后通过环境变量切换正式域名。

### D-026 2.0.4 改为邮箱预绑定并支持多人任务关系

日期：2026-06-08。

决策：2.0.4 删除手机号字段，改为管理员上传姓名+邮箱表，通过飞书邮箱换 open_id 完成预绑定；母任务负责人、部门任务负责人、子任务负责人和子任务执行人全部支持多人。

背景：手机号属于私人信息，获取和维护需要额外工单；邮箱可从通讯录导出文件直接获得，更适合生产迁移前批量预绑定。任务实际推进中也存在多人负责、多人执行的情况，单人字段会造成权限和提醒遗漏。

影响：人员档案只保留邮箱作为辅助匹配字段；邮箱导入按姓名精确匹配，无重名时自动写入，冲突阻塞人工处理。多执行人子任务按执行人分别生成周更新和飞书提醒，旧 `owner_id` / `executor_id` 仅作为兼容首人字段保留。

### D-027 2.0.5 先修显示刷新并做会议看板美观优化

日期：2026-06-08。

决策：2.0.5 先修复任务负责人/执行人保存后页面显示不刷新的问题，并推进会议看板第一轮美化；本轮不做会议看板关联性、联动筛选或深度钻取。

背景：2.0.4 实测中出现母任务负责人保存提示成功但列表和详情显示没有同步变化的体验问题。会议看板还需要先提升基础视觉层级和表格可读性，再进入后续关联能力设计。

影响：后端更新任务人员关系后需要刷新并返回最新多人关系，前端保存后等待重新拉取数据。会议看板风险与逾期汇总采用固定列宽、省略显示和悬停查看完整内容。本地默认入口继续使用 `8080`，生产内网端口通过环境变量设为 `28081`。

### D-028 2.0.6 小屏优先采用自动收起侧栏和列宽收敛

日期：2026-06-08。

决策：2.0.6 针对中小屏显示器先采用侧栏自动收起、页眉紧凑排列、表格列宽收敛和长文本省略提示，不做表格卡片化。

### D-031 2.0.9 看板数据必须可追溯到明细

### D-032 2.3.4 部门负责人和任务负责人按层级分权

日期：2026-06-11。

决策：部门负责人以 `department_owner` 角色加所属部门认定，负责查看本部门牵头母任务并拆分、管理相关部门任务；任务负责人以部门任务负责人关系认定，只负责将本人部门任务拆分为子任务。子任务负责人不再独立维护，强制继承部门任务负责人。

背景：历史导入把部门任务负责人同时赋予部门负责人和任务负责人角色，导致“部门管理责任”和“具体任务拆解责任”混在一起，存在母任务和部门任务越权风险。

影响：普通同部门人员不再自动看到部门任务；旧的重叠角色在迁移时按安全原则清理，真正的部门负责人需要由人员权限明确授予。母任务负责人保留原有授权，但不会自动获得子任务拆分权。

### D-033 2.3.4 使用引导采用系统层和板块层双层模型

日期：2026-06-11。

决策：使用引导分为首次进入系统的框架引导和首次主动点击左侧板块的专项引导，并按用户、引导键和版本分别记录。角色固定为总经办会议相关、部门负责人、任务负责人、子任务执行者和观察者，管理员不再作为业务引导角色。

背景：单一五步引导只能介绍页面结构，无法同时覆盖系统任务框架和各板块的实际工作方法；登录后连续弹出多套引导又会干扰领导使用。

影响：2.3.4 先交付总经办框架引导和会议看板专项引导。专项引导只在首次主动点击左侧菜单时出现，默认落地、刷新和飞书深链不触发；其他角色按后续版本逐个完善。

### D-034 2.3.5 部门负责人引导区分管理责任和执行责任

日期：2026-06-11。

决策：部门负责人拥有独立系统框架引导，并固定提供母任务管理和部门任务两个板块引导；仅当本人存在有效子任务执行关系时，额外提供子任务执行板块引导。

背景：部门负责人常同时兼任任务负责人或子任务执行人。如果只按最高角色展示管理引导，会遮蔽本人仍需提交周更新的执行责任；如果对所有部门负责人都展示子任务执行引导，又会打扰没有执行任务的管理者。

影响：部门负责人不再使用旧通用短引导。引导文案明确区分部门管理责任、任务负责人拆解责任和执行人周更新责任；本版不改变权限、任务数据和角色分配。

### D-035 2.3.6 任务负责人引导聚焦拆解与跟踪闭环

日期：2026-06-11。

决策：任务负责人拥有独立系统框架引导，并固定提供部门任务板块引导；仅当本人存在有效负责或执行子任务时，额外提供子任务执行板块引导。

背景：任务负责人常同时兼任子任务执行人。如果只讲部门任务拆解，会遗漏本人仍需提交周更新的执行责任；如果对没有子任务关系的任务负责人展示子任务引导，又会造成无入口、无数据的干扰。

影响：任务负责人不再使用旧通用短引导。引导文案强调任务负责人不能进入母任务拆分职责，只负责本人部门任务的子任务拆解、执行人指定、进展跟踪和风险登记；本版不改变权限、任务数据和角色分配。

### D-036 2.3.7 子任务执行者引导聚焦本人填报闭环

日期：2026-06-11。

决策：子任务执行者拥有独立系统框架引导；仅当本人存在有效执行子任务时，额外提供子任务执行板块引导。

背景：执行者的核心工作不是拆解和管理，而是按周维护本人任务进展。如果没有有效执行任务仍弹子任务板块引导，会把用户带到无数据页面，降低引导可信度。

影响：子任务执行者不再使用旧通用短引导。引导文案聚焦本人任务、开启任务、周更新提交、风险登记和完成状态；本版不改变权限、任务数据和角色分配。

### D-037 2.3.8 观察者引导优先覆盖多重身份审阅场景

日期：2026-06-11。

决策：总经办仍为最高引导优先级；带 `observer` 角色的用户优先展示观察者引导，再判断部门负责人、任务负责人和子任务执行者身份。观察者固定提供会议看板、母任务管理、部门任务和历史时间线专项引导，仅在本人存在有效执行任务时提供子任务执行引导。

背景：陈俊伊同时具备观察者、任务负责人和执行者关系。如果继续按任务负责人优先，会把其主要审阅定位误导为部门任务拆解；但完全忽略其执行关系，又会遗漏仍需按执行人身份提交周更新的责任。

影响：观察者不获得任何新增写权限。引导文案以全局只读审阅、任务追溯和会议准备为主，同时轻量提示多重身份下仍需处理本人负责或执行的具体任务。

决策：4.2.0 只做飞书汇报集成可行性和任务治理方案验证，不新增业务功能、不新增数据库表、不制作生产离线包。产品方向采用“任务治理优先”：临时或日常工作进入待归类机制，最终补拆到任务树或关闭为非任务型记录，不建设长期游离在战略目标之外的日常任务池。

背景：人事希望把飞书汇报、周报日报和绩效考核纳入系统，核心担忧是现有任务树可能不能覆盖全部工作表达。大领导侧更关注公司任务必须能追溯到战略目标。飞书官方汇报开放能力当前主要是查询规则和查询任务，未发现创建、提交或更新汇报内容的确定接口；飞书绩效补充信息导入不等同于飞书汇报周报提交。

影响：系统内生成个人周报、复制草稿、飞书卡片提醒和读取飞书汇报数据可继续评估；自动提交回飞书原生汇报周报暂不承诺。后续可先做“待归类事项”原型和“个人周报聚合页”，飞书回写只有在验证到正式 API 或稳定写入路径后再独立立项。

### D-048 4.2.1 工作台承接待归类事项

日期：2026-06-12。

决策：4.2.1 将“待归类事项”升级为工作台核心机制。所有人都应有入口提交临时或急性事项，首版只填写事项内容和责任人；责任人再判断挂到现有任务、补部门任务、提出母任务缺失诉求或关闭为非任务型记录。

背景：临时急性任务不可能全部提前预判，但长期放在任务树外会削弱战略目标到执行任务的治理闭环。员工需要一个低门槛入口，总经办和负责人则需要看到哪些事项暴露了部门任务或母任务缺失。

影响：后续实现时，工作台应恢复为登录默认页，按用户多重身份叠加展示行动模块。管理员优先看通知失败、人员信息缺失和系统风险；总经办秘书优先看母任务缺失诉求、部门任务缺失诉求、风险、逾期和未更新情况；负责人和执行人则看本人待处理任务与待归类事项。待归类事项在正式挂入任务树前不进入任务推进统计，关闭为非任务型记录的事项只进入个人周报材料。

### D-049 4.3.x 先完成执行者侧闭环

日期：2026-06-12。

决策：4.3.0 只做执行者工作台与待归类事项分版本规划，不落地代码、不新增表、不制作生产离线包。4.3.x 只覆盖执行者侧：工作台、本人任务、待归类事项提交、事项状态查看和个人周报材料雏形。

背景：待归类事项会牵动执行者、责任人、任务负责人、部门负责人和总经办秘书多个角色。如果一次性做全链路，容易把归类权限、任务挂接和会议诉求混在一起，验收节奏也会失控。先完成执行者侧，可以把“员工怎么提交、怎么看状态、怎么形成周报材料”跑顺。

影响：4.3.1 做执行者工作台框架，4.3.2 做待归类事项提交入口，4.3.3 做执行者个人周报材料雏形，4.3.4 做执行者体验收尾与 4.4 准备。责任人归类处理、任务负责人挂接任务、部门负责人补部门任务、总经办秘书处理母任务缺失均不得提前混入 4.3.x。
