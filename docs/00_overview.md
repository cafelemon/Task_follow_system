# 公司工作任务跟踪系统总览

## 1. 文档用途

本文档用于说明公司工作任务跟踪系统的整体定位、建设边界、核心对象和关键设计方向。后续产品需求、架构设计、验收清单和开发任务都应以本文档为基础。

## 2. 系统定位

公司工作任务跟踪系统是面向全公司长期使用的正式任务管理系统。

系统要解决的是公司级任务从提出、拆分、执行、每周更新、会议查看到历史追踪的完整流程。飞书多维表格可以继续承担过渡、导出或展示作用，但不再作为主业务系统。

本系统不是再做一张表，而是建设一套可长期运行、可追溯、可校验、可权限控制的公司任务管理平台。

## 3. 当前建设背景

当前任务跟踪主要依赖飞书多维表格完成任务录入、拆分、周更新、提醒和看板展示。多维表格适合作为轻量协作工具，但在长期公司级任务管理中存在明显边界：

- 历史进展依赖人工留存，无法自然形成任务时间线。
- 编号、关联和人员字段容易手填错误。
- 表格视图难以满足管理层会议、部门汇总和执行人待办场景。
- 权限粒度不够细，难以表达负责人、执行人、部门负责人、管理层等不同角色。
- 自动化触发容易受到错误字段影响，后续修正成本高。

新系统应把数据模型、权限、校验、提醒、历史记录和 Web 页面作为一体化能力设计。

## 4. 部署口径

本系统不能只支持本地局域网访问。由于公司存在出差、分公司和异地办公场景，系统需要通过反向代理对外提供安全访问。

初步部署方向：
- docker 部署
- 服务可部署在公司 GPU 服务器或其他稳定内网服务器上。
- 通过已有反向代理体系暴露访问入口。
- 支持 HTTPS、访问控制和必要安全策略。
- 内部网络访问和外部出差访问保持同一套身份与权限逻辑。
- 附件存储优先放在公司的 NAS 服务器上。

任务跟踪系统涉及全公司协同和长期填报，必须从第一版开始考虑外部访问便利性、安全性和可维护性。

## 5. 技术方向

建议技术栈：

- 后端：FastAPI。
- 数据库：PostgreSQL。
- 前端：现代 Web 前端框架，具体选型后续确认。
- 飞书接入：企业自建应用机器人、消息卡片、open_id 用户身份、部门同步。
- 部署：服务器部署、反向代理、后台任务调度、日志和备份。

核心后台能力：

- 用户与部门同步。
- 角色和权限控制。
- 任务、子任务、周更新和历史事件管理。
- 自动化工作流。
- 飞书消息推送和卡片交互。
- 定时提醒和逾期检查。
- 数据导出和历史迁移。

## 6. 与现有飞书桥接系统的关系

现有飞书桥接系统已经具备可复用经验：

- 飞书机器人长连接。
- open_id 用户识别。
- 用户和部门信息同步。
- 消息处理队列。
- 权限路由思路。
- FastAPI 服务结构。

新系统可以参考这些能力，但不应直接复用知识库的粗粒度权限模型。任务跟踪系统的权限需要更细：

- 谁能看某个上层任务。
- 谁能拆分某个任务。
- 谁能编辑某个子任务。
- 谁能填写某条周更新。
- 谁能查看部门汇总。
- 谁能查看全公司看板。
- 谁能导出和管理系统。

因此，飞书桥接系统适合作为身份、消息和接入经验参考，任务业务模型和权限模型需要重新设计。

## 7. 核心数据对象

第一版建议围绕以下对象建模：

| 对象 | 说明 |
| --- | --- |
| 用户 | 绑定飞书 open_id、姓名、部门和系统角色 |
| 部门 | 由系统维护或从组织信息同步，用于权限和统计 |
| 战略目标 | 总经办定下的年度公司战略目标任务 |
| 母任务 | 总经办或管理层提出的公司级或部门级任务，由总经办确立负责人 |
| 部门任务 | 对母任务分配到各部门的任务项，由总经办或母任务负责人确立负责人 |
| 子任务 | 任务负责人拆分出的执行项，由子任务执行者每周汇报 |
| 周更新 | 执行人每周填写的进展、计划、风险和附件 |
| 任务事件 | 创建、拆分、延期、变更、完成等历史动作 |
| 通知记录 | 飞书提醒、卡片推送、用户点击和处理结果 |

任务历史不清空，每次更新都形成可追踪记录。用户可以更新本周子任务进度，过去进度默认可读、可审计，不作为日常覆盖对象。

## 8. 入口设计

系统不只依赖一个入口：

- Web 页面：主操作入口，承载任务拆分、看板、时间线和管理功能。
- 飞书机器人：提醒入口，推送待办、填报、未更新、会议看板。
- 日报或周报：后续可关联任务数据，用于汇总个人工作，第一版暂不强行打通。
- Base：作为过渡产品和参考样本，保留部分值得迁移的设计经验。

## 9. 权限方向

权限应采用系统内细粒度控制，不只依赖飞书群或多维表格权限。

初步角色：

- 系统管理员。
- 总经办或秘书。
- 母任务负责人。
- 部门负责人。
- 任务负责人。
- 子任务执行人。
- 信息中心维护人员。
- 组织与人才发展中心观察角色。
- 各部门成员

角色可以多重，采取权限组合

权限判断优先基于：
- 飞书 open_id。
- 所属部门。
- 系统角色。
- 任务负责人关系。
- 子任务执行人关系。
- 是否拥有全局查看或部门查看权限。

## 10. 与 Base 的关系

Base 的定位调整为：

- 过渡期继续使用现有表格。
- 新系统上线后可导入历史快照。
- 必要时向 Base 同步部分展示字段。
- 不再通过 Base 自动化控制主流程。
- 不再依赖周日清空前人工留存维持历史。

## 11. 后续文档方向

后续需要继续补充和细化：

- 数据库模型设计。
- 接口设计。
- 飞书消息卡片设计。
- 权限矩阵。
- 部署和反向代理方案。
- 历史数据迁移方案。
- MVP 开发排期。
